# 日志使用说明

极简调试日志系统，前端加现场打点、后端关键路径打点，统一追加写入 `paim.log`。仅用于排查，写文件失败时静默，不阻塞业务。

## 日志文件位置

- **开发/e2e（debug 构建）**：`<项目根>/paim.log`（经 `CARGO_MANIFEST_DIR` 编译期定位，不依赖工作目录）。
- **部署（release 构建）**：`<进程工作目录>/paim.log`。
- 路径在首次写日志时惰性计算一次。

## 日志格式

每行：`本地时间 [级别] 消息`

``` text
2026-08-23 12:00:00.123 [INFO] [FE] [App] mounted, route = /prompt
```

- 时间：本地时间，毫秒精度（`chrono::Local`）。
- 级别：`DEBUG` / `INFO` / `WARN` / `ERROR`。

## 日志级别控制（前后端统一）

前后端共用**一个全局最低级别开关**（`infra/logging.rs` 的 `MIN_LEVEL`），低于该级别的日志不落盘。启动时按优先级初始化（高→低）：

1. **运行时热切**：`set_log_level` 命令（前端 `commands.setLogLevel(level)`，或 `@/utils/logger` 的 `setLogLevel()` 助手）；切换后 emit `log-level-changed` 事件，前端缓存自动同步。查询当前级别用 `get_log_level`。
2. **环境变量** `PAIM_LOG`（`debug`/`info`/`warn`/`error`，大小写不敏感）——临时调试不改配置文件；值无效记 WARN 后忽略。
3. **配置文件** `paim-config.toml`：**按构建类型分离**——dev 在项目根，release 在应用所在目录（进程工作目录，通常即安装目录，与 `paim.log` 同目录）。两边各只含本环境的键：dev 是 `dev-log-level`，release 是 `release-log-level`。
   **文件不存在时应用会自动写入对应模板**（含注释与默认值），存在则一个字节都不动；解析失败或值无效记 WARN 后回落默认。写不进去（工作目录不可写）只记 WARN，不影响启动。
4. **内置默认**：release `WARN`、dev `INFO`（e2e 启动时由测试框架注入 `PAIM_LOG=debug`，实际跑 `DEBUG`）。

示例：

```toml
# 项目根 paim-config.toml（debug 构建读取）
dev-log-level = "info"
```

```toml
# 安装目录 paim-config.toml（release 构建读取，首次运行自动生成）
release-log-level = "warn"
```

- **零开销过滤**：后端 `log_*!` 宏先判级别再 `format!`，被过滤的日志零格式化开销；前端缓存级别本地预判，被过滤的日志不产生 IPC（缓存就绪前先放行，保证 boot 早期日志不丢）。
- **各场景默认**：`pnpm tauri dev` 为 `INFO`（日常降噪；排查时把项目根 `paim-config.toml` 的 `dev-log-level` 改成 `debug`，或临时 `PAIM_LOG=debug`，无需改代码）；e2e 为 `DEBUG`——[e2e-helpers.ts](../e2e/e2e-helpers.ts) spawn 应用时注入 `PAIM_LOG=debug` 保证全量埋点落盘（外部已显式设置 `PAIM_LOG` 时尊重外部值）；**release 为 `WARN`**——前端 DEV 硬门已移除，发布版 `warn`/`error` 照常落盘，出问题时临时 `PAIM_LOG=debug` 或热切复现，无需重新构建。**停机排查的关键路径一律用 `WARN` 级**（锁等待/持锁、详情保存慢、embedding 冷却、索引中止），所以 release 默认级别下这些信号仍然落盘（见第五节）。

## 一、后端（Rust）

在 `src-tauri/src/infra/logging.rs` 提供了 4 个宏，crate 内任意模块可直接使用：

```rust
log_debug!("...");
log_info!("...");
log_warn!("...");
log_error!("...");
```

级别由上述全局开关统一过滤，无需在调用点自行判断。

## 二、前端（TS/Vue）

使用 `src/utils/logger.ts` 导出的 `log` 对象，按级别打点（**dev 与 release 均生效**，级别预判在被过滤时不产生 IPC）：

```ts
import { log } from "@/utils/logger";

log.debug("消息文本");
log.info("消息文本", { id, step }); // 多参用空格拼接，对象自动 JSON 序列化
log.warn("消息文本");
log.error("消息文本");

await setLogLevel("debug"); // 可选：运行时热切全局级别
```

前端通过 `commands.logMsg(level, message)` 上报后端（tauri-specta 生成的类型安全绑定，见 [新增命令说明(tauri-specta版).md](./新增命令说明(tauri-specta版).md)），后端会加上 `[FE]` 前缀写入文件。
`level` 对应后端映射：`debug` / `info` / `warn` / `error`。

## 三、e2e 场景

e2e 里有两类日志，**全部只写 `<项目根>/paim.log`，控制台不再主动输出**（playwright 自身的
用例结果行如 `ok 1 ...` 除外）：

1. **测试侧日志**：e2e 目录下的文件（用例步骤、CDP 连接、实例进程退出等）通过
   `e2e/e2e-logger.ts` 的 `e2eLog.info/error` 写入——调用方式与前端 logger 一致
   （多参拼接、对象 JSON 序列化），带 `[E2E w<n>]` 前缀标识所属 worker：

   ```ts
   import { e2eLog } from "./e2e-logger";

   e2eLog.info("[step] 已选择图像");
   e2eLog.info("[step] 已提交上传", { count: 1 }); // 对象自动 JSON 序列化
   e2eLog.error(`[http-error] ${res.status()} ${res.url()}`); // 失败类日志用 error 级
   ```

   测试侧输出级别由 `playwright.config.ts` 的 `PAIM_E2E_LOG_LEVEL` 控制（默认 `debug`，
   用例步骤、连接过程等全量落盘，便于排查）；跑全量嫌噪声多时临时改为 `warn`，
   只记 `pageerror`/失败请求/4xx 等异常信号。**该变量只管测试侧日志**，与应用侧级别无关。

2. **页面侧诊断**：fixture 里采集的 webview 控制台消息、失败请求与 ≥400 响应
   （`[webview]`/`[pageerror]`/`[req-failed]`/`[http-error]` 前缀）。失败请求中
   导航打断的在途请求（`net::ERR_ABORTED`）记 info 级，其余记 error 级。

应用侧（`[FE]` 前缀与后端日志）的级别走上文「日志级别控制」的全局开关（e2e 下 spawn 注入 `PAIM_LOG=debug`，实际为 `DEBUG`）。
排查 e2e 失败时按时间顺序读 `paim.log` 即可（多 worker 的行由 `[E2E w<n>]` 区分归属）。

## 四、使用建议

- 排查「启动即弹窗」「路由跳转」「组件挂载时机」等问题时，在 `main.ts`、`App.vue`、组件 `onMounted` / `watch` 处打点。
- 需要「应用打开时不残留 UI」的排查，可在启动后扫描 `document.querySelectorAll('.fixed.inset-0')` 并 `log.debug` 输出，确认是否有遮罩残留。
- 低频有效信号（如分页竞态的「丢弃过期响应」）保留 `WARN` 级，便于全量日志扫描时一眼定位；纯时序噪声（如挂载期的 `total=0` 跳过）用 `DEBUG` 级，避免淹没真信号。
- 日志是调试/临时用途（见文件头注释「仅用于排查，可随时移除」），问题定位后可清理埋点，不必长期保留。
- **后端不要用 `log::*`**：`log` facade 的 logger 只有 `tauri_plugin_log` 一个，而它只在 `cfg(debug_assertions)` 下注册（`lib.rs`）——release 构建里 `log::warn!`/`log::error!` **没有任何输出**。后端一律用 `crate::log_debug!/log_info!/log_warn!/log_error!`（写 `paim.log`）。

## 五、卡顿 / 「点了一下没反应」的排查口径

单连接 + 无超时锁 + 主线程同步命令是三类卡顿的共同结构（详见 [lessons.md](lessons.md) 第 12 / 14 / 28 节），下面几类日志就是为它们准备的：

- **db 锁等待 / 持锁**：连接是单连接 + Mutex（`infra/db.rs` 的 `DbConn`）。等待或持锁超过 **500ms** 记 WARN，且**等待中**（不是事后）就打出「谁在等 + 当前持锁者 + 已持多久」，卡住期间就有证据；μs 级微竞争不记（阈值内先短睡重试，日志本身是文件 IO，不能反过来拖慢主线程）：

  ``` text
  2026-10-06 15:00:00.123 [WARN] db 锁等待中 prompt.rs:278 —— 当前持有 thumbnail_service.rs:253 已 8420ms
  2026-10-06 15:00:08.551 [WARN] db 锁持有 8420ms（thumbnail_service.rs:253）
  ```

  第一行说明「谁被堵住」，第二行说明「谁堵了别人」；括号里是取锁的调用点，可直接定位到命令/领域函数。
- **详情保存**：`update_prompt_detail` / `update_image_detail` 成对埋点（开始 / 完成 + 耗时，>500ms 记 WARN），前端 `saveFields` 同样成对（`[PromptDetail] 保存开始` / `保存完成`）。**卡住的表现是「开始」有、「完成」没有**——保存路径不碰 embedding 服务，卡住只可能在取锁或写库两处。
- **缩略图懒自愈**：前端 `[SelfHeal] 开始校验 N 项` / `[SelfHeal] 校验完成 Xms`（DEBUG）+ `[SelfHeal] 校验慢`（≥2s，WARN）。它是「长时间持锁」最常见的来源（锁内整批解码 + 编码）。
- **embedding 服务（llama.cpp 不常驻）**：断路器打开、索引任务开始/结束与中止原因都是 WARN/INFO 级（`similarity.rs`），服务没起时先看这几行，再看设置页面板上的中止原因。
- 判读顺序：先按时间定位最后一条**没有配对「完成」的「开始」**，再找同一时间段里持锁最久的那条 WARN。
